About

Plan-It! is a web application designed to facilitate convenient planning, and easy scheduling of events without conflicts through syncing with other scheduling apps, and providing extensive event customisation available to users. 

Motivation

The hardest part about planning a meet-up is timing. Allow us to paint a picture of the average person’s typical attempt at trying to get his/her friends to hang out: Average Joe hasn’t seen his friends in a while and decides to invite them out for lunch sometime. He already has the name of a delicious restaurant chain in mind; all he needs now is to figure out when everyone is available. He sends out a text to the group chat and waits in anticipation. Ding! A notification chimes. The first of four friends has replied with a confusingly long description of his schedule. Over the next few days, the group chat fills with messages and important information gets lost in the sea of random chatter. Joe could somehow foresee the future at this point. It has now been two months since Joe sent that message. The last friend never replied. Nobody bothered to collate the timings. And the outing never happened.

That is why we decided to create Plan-It!—an app specially designed with users like Joe in mind. Besides meet-ups with friends, Plan-It! can be used for virtually any event, no matter how big or small. With the ability to import and save schedules from other apps, users no longer have to go through the hassle of manually checking and keying in their availability every time.

Aim

We hope that Plan-It! will help users plan group activities efficiently. By cutting down the amount of precious time wasted on deciding on the when, we believe that users can focus on the other details that truly matter, such as what to do and how to achieve it. Planning events should in no way be a daunting task. Our aim is for Plan-It! to bring convenience and ease for all our fellow planners, making the experience enjoyable for not just the event-goers.


User Stories

As a university student, I want to be able to identify my free time so that I can manage my workload more effectively.

As a planner in charge of an event, I want to be able to share event details quickly without having to think of how to format it.
As a planner of an urgent event, I want to be able to quickly identify the earliest time when everyone is free so the event can be held as soon as possible.
As a member of a group who frequently plans events, I want to be able to automatically indicate my preferences so that I do not have to keep replying to confirm events.

Database Structure


public schema

Naming Convention

Following convention, our table and column names are all in snake case. We chose to use the singular forms as it is more intuitive to refer to a table as the ‘user’ table, for example, as opposed to the table of ‘users’. Moreover, it makes the naming of bridge tables more convenient as we can simply concatenate the names of the two tables being joined without having to worry about singularisation.

The primary keys of the tables are in uuid format and the column name is simply ‘id’. We chose to use uuids instead of sequential id as it makes it harder to guess or enumerate ids, providing some form of data security. As for the column name, we chose not to use ‘[tablename]_id’ as we found it overly verbose and redundant to reference the column by ‘[tablename].[tablename]_id’.

However, at the end of the day, we believe the most important convention is to stick to a convention.


Data Relationships

In the public schema of our database, we have 6 tables:

user

While Supabase Auth provides an auth schema to help with the implementation of user authentication and authorisation, the data captured by the Auth system is prescribed and Supabase does not recommend making any modifications to the auth.users table. However, we wanted to store additional user information such as username and display name. Hence, we made our own user table to serve as an extension to Supabase’s default user management system and is defined as such:

create table public.user (
 id uuid not null default auth.uid (),
 username text not null,
 display_name text not null,
 email text not null,
 constraint user_pkey primary key (id),
 constraint user_email_key unique (email),
 constraint user_username_key unique (username),
 constraint user_id_fkey foreign KEY (id) references auth.users (id) on delete CASCADE
) TABLESPACE pg_default;
user table definition

The primary key references auth.users.id in a one-to-one relationship. Each user in Supabase Auth has a profile which is represented as a row in public.user. The default value of this column is the User’s unique id as defined by Supabase Auth. The cascade on delete action ensures that should a user in auth.users be deleted, the corresponding record in public.user will also be deleted. This prevents extraneous storage usage as the profiles of users who no longer exist in the Auth system will not be kept for longer than necessary.

Although auth.users already stores the email addresses of users, we decided to include an email column in public.user anyway so as to reduce reliance on Supabase Auth which is subject to changes. Moreover, this eliminates the need for joining tables when retrieving users’ email addresses, increasing the efficiency of our application.

RLS Policies

Row Level Security (RLS) policies play a vital role in database security as they prevent unauthorised users from gaining access to unprotected data. Moreover, they simplify the querying process as different users will have different views of the same table, reducing the need for complicated filters in the code. In this section, we will be explaining how we implemented our RLS policies in-depth.

create policy "Enable read access for all users"
on "public"."user"
as PERMISSIVE
for SELECT
to anon, authenticated
using (
 true
);
select policy

The select policy allows anonymous and authenticated users to read user data. Based on the principle of least privilege, we should only grant users the minimum level of access required to perform their tasks. Authenticated users should be allowed to view all other users’ data as this permission is required to display user profiles.

In this case, granting read-access to unauthenticated users is necessary for performing checks such as whether an email address is already in use, whether a username is taken, or whether an account exists. These checks are performed during the registration and login process, before users are authenticated. Hence, it is not sufficient to only grant access to authenticated users, otherwise, it would be impossible for unauthenticated users to login or register.

create policy "Enable insert for users based on user_id"
on "public"."user"
as PERMISSIVE
for INSERT
to authenticated
with check (
 (( SELECT auth.uid() AS uid) = id)
);
insert policy

The insert policy allows authenticated users to create a row if their user id matches the id of the row being inserted. The user id is connected to the user’s access token, which is issued once a user has registered for an account. This means that users are able to set their usernames and display names upon creating their profiles.

To prevent performance issues, we followed the Supabase Docs in wrapping auth.uid() in a select subquery which ensures that the function only gets called once per query and not for every row.

create policy "Enable update for users based on user_id"
on "public"."user"
as PERMISSIVE
for UPDATE
to authenticated
using (
 (( SELECT auth.uid() AS uid) = id)
) with check (
 (( SELECT auth.uid() AS uid) = id)
);
update policy

The update policy allows authenticated users to modify their own data only. The policy checks that both the existing row being updated and the new row after the update matches the user’s id. This means that users can change their profile information while protecting other users’ profiles from being modified.

create policy "Enable delete for users based on user_id"
on "public"."user"
as PERMISSIVE
for DELETE
to authenticated
using (
 (( SELECT auth.uid() AS uid) = id)
);
delete policy

The delete policy allows authenticated users to delete their own data only. This means that users can delete their account should they wish to do so.

event

To keep track of events created by users, we originally considered having 3 separate tables, each storing a different type of event. However, we realised that doing so would give rise to much redundancy since the logic to handle these events are largely similar. Moreover, having just one table would make data management simpler and more efficient since all event information can be retrieved with a single query. Hence, we settled on an event table defined as follows:

create table public.event (
 id uuid not null default gen_random_uuid (),
 creator_id uuid not null default auth.uid (),
 group_id uuid null,
 title text not null,
 description text null,
 start_time timestamp without time zone null,
 end_time timestamp without time zone null,
 source text null,
 constraint event_pkey primary key (id),
 constraint event_creator_id_fkey foreign KEY (creator_id) references "user" (id) on delete CASCADE,
 constraint event_group_id_fkey foreign KEY (group_id) references "group" (id) on delete CASCADE
) TABLESPACE pg_default;
event table definition

Initially, for all tables in the public schema, we set the foreign keys containing a user id to reference auth.users.id like in the user table. However, this was not the best approach as mixing authentication data with application-specific data compromised data integrity. Moreover, since we have already created a user table to store additional information, referencing public.user.id directly makes querying data less complicated.

Currently, when a user deletes their account, all events created by them will also be deleted. However, we are considering changing this design as other users in the shared event may wish to still proceed with the event even without the user who initiated it. Some other considerations include permissions to set details for the event since the current implementation only allows the creator to do so.

To differentiate group events from personal events and shared events, the event table includes a group_id column which is nullable. If group_id is not null, it means that the event is tied to a group, and is hence a group event. On deletion of a group, all events associated with the group will also be deleted.

The source column keeps track of where events are imported from. This comes in handy when dealing with events from external sources and will be elaborated on in the subsequent sections.

RLS Policies

While writing the RLS policies for the event table, we encountered many problems relating to PostgreSQL. To illustrate with an example, the first rendition of our select policy went as follows:

create policy "Users can view events they are in"
on "public"."event"
as PERMISSIVE
for SELECT
to authenticated
using (
 ((( SELECT auth.uid() AS uid) = creator_id)
 OR (id IN (
   SELECT user_event.event_id
   FROM user_event
   WHERE (user_event.user_id = ( SELECT auth.uid() AS uid))
 )))
);
event select policy

The policy is quite self-explanatory—it allows users to view the rows for which they are the creator of the event or are part of the event. While this policy seems fine on its own, the issue becomes apparent when combined with the insert policy of the user_event table:

create policy "Users can invite people to their events"
on "public"."user_event"
as PERMISSIVE
for INSERT
to authenticated
with check (
 (event_id IN (
   SELECT event.creator_id
   FROM event
   WHERE (event.creator_id = ( SELECT auth.uid() AS uid))
 ))
);
user_event insert policy

The policy checks that the user inserting the row is the creator of the event by comparing the event id against the records of all the events created by the user in the event table.

The error we kept getting was ‘infinite recursion detected in policy for relation’. Upon further investigation, we found out that this is a PostgreSQL safeguard to prevent circular logic in RLS policies and occurs when the RLS policies for two tables reference each other. The annoying part is that even if the policy logic does not actually recurse during the query, PostgreSQL just refuses to risk it and raises an error anyway.

To circumvent this issue, we made security definer functions to bypass RLS. These security definer functions are created with the role of a postgres user and are executed with the privileges of the function owner, allowing us to run queries that require high privileges in a controlled fashion.

CREATE FUNCTION is_invited_to(_user_id uuid, _event_id uuid) RETURNS bool AS $$
SELECT EXISTS (
 SELECT 1
 FROM user_event ue
 WHERE ue.event_id = _event_id
 AND ue.user_id = _user_id
);
$$ LANGUAGE sql SECURITY DEFINER;
is_invited_to function

The is_invited_to function checks if a user has been invited to an event by searching for a row in user_event where the user_id and event_id correspond to the given user id and event id.

CREATE FUNCTION is_member_of(_user_id uuid, _group_id uuid) RETURNS bool AS $$
SELECT EXISTS (
 SELECT 1
 FROM user_group ug
 WHERE ug.group_id = _group_id
 AND ug.user_id = _user_id
);
$$ LANGUAGE sql SECURITY DEFINER;
is_member_of function

Similarly, the is_member_of function checks if a user belongs to a group by searching for a row in user_group where the user_id and group_id correspond to the given user id and group id.

Since security definer functions provide admin level privileges, to prevent misuse, we ensured that these functions are stored in a private schema which is not exposed in the api settings.

That being said, we can finally move on to the actual implementation of the RLS policies for the event table:

create policy "Users can view their own and shared events"
on "public"."event"
as PERMISSIVE
for SELECT
to authenticated
using (
 ((( SELECT auth.uid() AS uid) = creator_id)
 OR private.is_invited_to(( SELECT auth.uid() AS uid), id)
 OR private.is_member_of(( SELECT auth.uid() AS uid), group_id))
);
select policy

The select policy allows users to view an event if they are the creator of the event, are an invitee of the event, or are a member of the group to which the event belongs to. Although creators of the event are by default invitees of the event, we still have to include the first condition as we need the event id to insert rows into the user_event table. In other words, the event must be created before invitees can be added.

create policy "Users can create events for themselves and their groups"
on "public"."event"
as PERMISSIVE
for INSERT
to authenticated
with check (
 ((( SELECT auth.uid() AS uid) = creator_id)
 AND ((group_id IS NULL)
   OR private.is_member_of(creator_id, group_id)))
);
insert policy

The insert policy allows users to create an event if the event is not a group event or if they are a member of the group for which they wish to create the event.

The update and delete policies are rather straightforward, hence we shall skip over their explanation.

) with check (

);
update policy

 user_id uuid not null default auth.uid (),
 event_id uuid not null,

4. Core Feature: Schedule Timings

Algorithm

Finding the available timings for an event is essentially finding the gaps between the combined schedules of the attendees. Since dates in JavaScript can be represented as a number, we can come up with an algorithm to get the missing intervals in a sorted list of numbers and apply it to the event timings.

/**
* Given a sorted list of intervals and a range, return the complement list of intervals
*
* @param intervals
* @param rangeStart
* @param rangeEnd
* @returns list of intervals
*/
function getMissingIntervals(
 intervals: number[][],
 rangeStart: number,
 rangeEnd: number
) {
 const missing = [];


 let prevEnd = rangeStart;


 for (const interval of intervals) {
   const start = interval[0];
   const end = interval[1];


   if (start > prevEnd) {
     missing.push([prevEnd, start]);
   }


   prevEnd = Math.max(prevEnd, end);
 }


 if (prevEnd < rangeEnd) {
   missing.push([prevEnd, rangeEnd]);
 }


 return missing;
}
calendarService: getMissingIntervals function

For each interval in the list of intervals, we keep track of the start and end of the interval. If the start of the current interval is greater than the largest end we have encountered so far, there is a gap in the intervals and we add the gap to the result. At the end of the loop, we check if the last interval in the list exceeds the range given. If not, there is a gap from the last interval to the end of the range, and we add the gap to the result as well.

When the creator closes the poll, the timing with the most number of votes will be chosen for the event. /**
* Finalises the poll by choosing the most-voted timing.
* If there is a tie, the earliest timing is selected.
* @param eventId - ID of the event whose poll is being finalised.
*/
export async function finalisePoll(eventId: string): Promise<void> {
 const timings = await getPollTimings(eventId);
 const votes = await getPollVotes(eventId);


 const voteCounts: Record<string, number> = {};
 for (const vote of votes) {
   voteCounts[vote.timing_id] = (voteCounts[vote.timing_id] || 0) + 1;
 }


 const sorted = timings.sort((a, b) => {
   const vA = voteCounts[a.id] || 0;
   const vB = voteCounts[b.id] || 0;
   if (vA !== vB) return vB - vA;
   return new Date(a.start_time).getTime() - new Date(b.start_time).getTime();
 });


 const top = sorted[0];
 if (!top) return;

   .from("event")

   .eq("id", eventId)

 await finaliseEvent(creator!.creator_id, eventId, {

     const startTime = new Date(start).getTime();

     const rangeLimitTime = rangeLimit.getTime();


     return startTime >= nowTime && startTime <= rangeLimitTime;
   });


   const attendees = await getAttendees(currentEvent.id);


   const userMap = Object.fromEntries(attendees.map(a => [a.id, a.username]));


   const allEvents = (
     await Promise.all(
       attendees.map(async ({ id }) => {
         const events = await getEvents(id);
         return events.map((e) => ({ ...e, ownerId: id }));
       })
     )
   ).flat();
   const softClashes = filtered.flatMap(({ start, end }) => {
     const thisStart = toUTC(start).getTime();
     const thisEnd = toUTC(end).getTime();


     const overlappingEvents = allEvents.filter((event) => {
       if (!event.start_time || !event.end_time) return false;
       const eStart = toUTC(event.start_time).getTime();
       const eEnd = toUTC(event.end_time).getTime();
       return thisStart < eEnd && thisEnd > eStart;
     });


     const hasCompulsory = overlappingEvents.some((event) => event.label === "compulsory");
     if (hasCompulsory) return [];


     const softOnly = overlappingEvents.filter(
       (event) => event.label === "flexible" || event.label === "optional"
     );


     return softOnly.map((event) => ({
       start,
       end,
       label: event.label as "flexible" | "optional",
       title: event.creator_id === userId ? event.title : undefined,
       ownerName: event.ownerId === userId ? "you" : userMap[event.ownerId] || "a user",
     }));
   });
  
   setSoftConflicts(softClashes);
   setTimings(filtered);
 };

7. Extension Feature: Event Recurrence

Upon creating an event, users can choose to set the event to repeat either weekly, monthly or annually. When finding available timings, Plan-It! will alter its algorithm to check for clashes with every recurrence of the event.

To keep track of recurring events, we added the columns recurrence and repeat_until to our event table. The recurrence column stores 3 possible values: ‘weekly’, ‘monthly’, and ‘annually’. The repeat_until column stores the date until which the event repeats. This provides clarity as to how far we should consider the timing for the recurring event, making the code for our algorithm less complex.

Calendar Display

ScheduleX provides an event recurrence plugin which allows us to display a recurring event. To use it, we converted the event details to follow the recurrence rule string format required by ScheduleX. If the event is non-recurring, we represent it as a recurring event which occurs only once. This reduces the complexity of the code as every event will have an r-rule attribute, meaning we do not have to handle different types of events (whether it is recurring or not), which is not trivial in TypeScript.

const toRRule = (recurrence: string | null, repeat_until: string | null) => {
   if (!recurrence || !repeat_until) {
     return `FREQ=DAILY;COUNT=1`;
   }


   const freq =
     recurrence === "annually" ? "YEARLY" : recurrence.toUpperCase();


   const until = toDate(repeat_until);


   return `FREQ=${freq};UNTIL=${until}`;
 };

/**
* Checks available timings for a recurring event based on recurrence type and range.
*
* @param userIds - list of user IDs on attendee list to check availability for
* @param baseStart - starting datetime (e.g. 2025-07-15T10:00)
* @param durationMinutes - duration of each event instance
* @param repeatUntil - ISO date (e.g. 2025-07-15)
* @param recurrence - recurrence type ("weekly", "monthly", or "annually")
* @returns true if all slots are free for everyone on the attendee list, false otherwise
*/
export async function getRecurringTimings({
 userIds,
 baseStart,
 durationMinutes,
 repeatUntil,
 recurrence,
 userMap,
}: {
 userIds: string[];
 baseStart: string;
 durationMinutes: number;
 repeatUntil: string;
 recurrence: "weekly" | "monthly" | "annually";
 userMap: Record<string, string>;
}) {
 if (!baseStart || !durationMinutes || !repeatUntil) {
   return { conflict: false };
 }


 const start = new Date(baseStart);
 const until = new Date(repeatUntil);


 const allInstances: [Date, Date][] = [];


 let current = new Date(start);
 while (current <= until) {
   const instanceStart = new Date(current);
   const instanceEnd = new Date(
     current.getTime() + durationMinutes * 60 * 1000
   );
   allInstances.push([instanceStart, instanceEnd]);


   if (recurrence === "weekly") {
     current.setDate(current.getDate() + 7);
   } else if (recurrence === "monthly") {
     current.setMonth(current.getMonth() + 1);
   } else if (recurrence === "annually") {
     current.setFullYear(current.getFullYear() + 1);
   }
 }


 for (const userId of userIds) {
   const events = await getEvents(userId);


   for (const [recStart, recEnd] of allInstances) {
     const conflict = events.find((e) => {
       if (!e.start_time || !e.end_time) return false;
       const evStart = new Date(e.start_time);
       const evEnd = new Date(e.end_time);
       return recStart < evEnd && recEnd > evStart;
     });


     if (conflict) {
       const start = new Date(conflict.start_time!).toLocaleString();
       const end = new Date(conflict.end_time!).toLocaleString();
       const isSelf = userId === conflict.creator_id;


       const title = conflict.title || "Untitled Event";


       return {
         conflict: true,
         message: `Conflict with ${title} (${start} - ${end}) for ${
           userMap[userId] || "an attendee"
         }`,
       };
     }
   }
 }


 return { conflict: false };
}

Tech Stack

React.js

React provided component-based coding that allowed us to keep our UI components organised and reusable.

TypeScript

We chose TypeScript over JavaScript as it ensured type safety, enabling us to write our code more efficiently by making the code easier to trace and debug.

CSS

We stuck with vanilla CSS instead of using Tailwind. This was because of compatibility issues, with our project being created with Create React App (CRA), which did not support Tailwind out of the box. Setting it up required additional downloads and configuration that introduced installment issues.

Furthermore, the introduction of Tailwind would lead to a steeper learning curve due to its new syntax and class utilities. Sticking to the vanilla CSS allowed both members to spend more time and focus on the main features of our app, especially with the tight schedule with the milestones.

Supabase

We chose to use Supabase based on recommendations by advisors during the Milestone meetings. This was also due to Supabase’s all-in-one capabilities, offering authentication policies to restrict user access to certain data unless it pertains to them, ensuring data security, as well as easy data querying and throwing Postgres errors to catch if something goes wrong, facilitating debugging. Furthermore, there are a wide variety of tutorials available on YouTube to teach us how to use Supabase. This allowed us to implement complex features like login, adding events, and making groups without having to create our own backend server, which considerably increased the convenience and speed of development.

Node.js

Due to us choosing to use Supabase instead, we did not need to use the traditional backend server setup of Node.js + Express.js. This simplified our backend setup and instead allowed us to focus on coding the main features. However, we still used Node.js to power our React development server, using commands such as ‘npm install’ and ‘npm start’ to run and build our frontend. We chose to use Node.js for this instead of Next.js because we used Supabase for our backend and thus did not need the more complicated Next.js APIs to build our backend. Using Next.js would have increased complexity without any notable benefits for our app and hence Node.js was the best choice.

File Management

We used a recursive format to manage our files, making it easier to navigate. In the src folder, we have a pages folder which contains all the pages in our application. In the folder for each page, there is a folder for the subpages and another folder for the components shared across these subpages, and so on and so forth. This file management system made it easier for us to find the respective files and also know where to place newly created files.


src folder

We also used CSS modules, which helped us stay organised by having different CSS files for different components instead of having to think of a complicated naming convention for components in a global CSS file.

Coding Practices

Keep It Simple, Stupid (KISS)

Throughout our application, we made sure to pick simple and easily understandable naming conventions. Additionally, we tried to ensure that our code is not too complex.

Don’t Repeat Yourself (DRY)

One way we applied DRY was to create different components for different parts of a page. This allowed us to reuse components for features which functioned similarly in different pages.

Moreover, when applicable, we abstracted certain logic into their own functions, making it easier to reuse the logic.

Code Commenting

For complicated functions and logic, we left comments to make it easier for the other party or our future selves to understand. This can be seen in the code excerpts throughout this document.

Code Review and Pair Programming

In order to work efficiently together, we constantly kept each other up to date on the work we have done. This allowed us to have realistic expectations on the timeline of our project. When commits were pushed to GitHub, we made sure to read and understand the updated code. If any part of the code was confusing, we would clarify with the other member, and clean up the code if need be.

Version Control using Git/GitHub

For each feature that we coded, we created a new branch. Each member would work on a feature until it was completed, then submit a merge request to the repository once they were done, to merge into main. Thus, we ensured that we committed regularly once a logical component was completed and ensured each commit encapsulated only a single logical change. This way, it was easy to track bugs once they appeared. Furthermore, commit messages were also concise, with a standardised naming convention of capitalising the first word and using present tense, so that by looking at the title, we could see what each commit was achieving. Thus, it was easy to switch back to previous commits if needed. 


Commits

By submitting merge requests, we chose to merge only when both members had reviewed the code and approved the merge. In the case of merge conflicts, we discussed which parts of the code to keep to ensure that we were both in agreement. Thus, both members were up to date and aligned in their vision of what the app was trying to achieve and could continue coding their separate components without confusion regarding previous code, and resolving any possible miscommunications about each other’s code before they arose.

Type-safe Development using TypeScript

While we initially used JavaScript and JSX, we eventually decided to switch all our JavaScript code over into TypeScript instead to ensure type safety, helping to reduce bugs and runtime errors. The code was also easier to predict and understand while looking through due to the function return types and inputs being clearly listed out, allowing us to see the gist of what each function was doing at a glance.

Modular Code Structure

We separated features into well-defined modules such as the service files like calendarService and friendService to communicate with the backend database, as well as UI components such as FriendPage, SendFriendRequest, and EventPage being organised by features. This made the code easier to test and debug.
